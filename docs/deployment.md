# Deploy Naija Tickets Partner Demo as a separate Vercel project

This project is the **external organiser website**, not the Naija Tickets ticketing backend or its sandbox database. Two independent deployments are involved:

1. Separate Naija Tickets sandbox backend → separate Supabase test project → Paystack test mode.
2. This Partner Demo → calls that sandbox through its server API.

The existing production Naija Tickets project must remain unchanged. Creating this demo did not provision the backend sandbox, a Supabase project or credentials.

## 1. Prepare the separate backend sandbox

Use the already implemented Phase 3 backend source in a **separate deployment** with its own isolated Supabase project and fictitious data. Apply that backend's version-controlled migrations to the test project; never change the live database's resource binding.

The sandbox operator configures its own Supabase keys, reachable `APP_URL`, Paystack `sk_test_…` secret, `INTEGRATIONS_RESOURCE_MODE=test`, distinct sandbox/live project references, matching private resource settings, dedicated integration signing secret/version and `INTEGRATIONS_CHECKOUT_ENABLED=true`. These settings belong to the sandbox backend, not this Partner Demo. See the existing Naija Tickets Phase 3 guide for the backend runbook.

Create a fixture organiser and published events there, assign them to an application and create a **Test** key in that sandbox's Developers & Integrations dashboard. Include:

- integration:read
- events:read
- tickets:read
- availability:read
- checkout:write
- orders:read

Test keys created in the production dashboard are not replicated to a different Supabase project. Register this partner's exact origin in the sandbox application's **Test website origins**. Local example: `http://localhost:3001`. Production-deployed demo example: `https://naija-tickets-partner-demo.vercel.app` (use the actual returned URL).

For test emails, use controlled recipients and the sandbox's own configured email provider. Never copy production customers or issue live event admissions for a demo.

## 3. Import into Vercel

1. Open Vercel → Add New → Project.
2. Import the **new partner demo repository**.
3. Name it `naija-tickets-partner-demo`.
4. Root Directory: the new repository root containing package.json, api/ and public/.
5. Framework Preset: **Other**. Node.js: **24.x**.
6. Build Command: `npm run build`. Output Directory: `public`. Keep the committed `vercel.json`.
7. Deploy the unconfigured website if necessary to obtain its stable project URL. It will show the setup state; no event or payment is fabricated.
8. Add the environment variables below for the Vercel environment you are testing, then redeploy. Do not assume a changed variable updates a running deployment.

[Vercel documents Node functions in the api directory](https://vercel.com/docs/functions/runtimes/node-js) and [project rewrites/configuration](https://vercel.com/docs/project-configuration/vercel-json). This project uses one api/index.mjs function plus static assets and explicit page/API rewrites. It does not require a framework adapter, native image renderer or paid database.

## 4. Configure the partner server

| Variable            | Value                                                                                           |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| NAIJA_API_ORIGIN    | Exact HTTPS origin of the **separate Naija Tickets sandbox**, not the main production hostname. |
| NAIJA_TEST_API_KEY  | Test key generated by that sandbox's application. Store as a sensitive server variable.         |
| PARTNER_ORIGIN      | This Partner Demo's exact stable HTTPS URL.                                                     |
| DEMO_SESSION_SECRET | A separately generated persistent random 32-byte base64url value. Store as sensitive.           |

None use a public/browser variable prefix. Do not put a Paystack secret, Supabase service key, admin credential or production API key in this project. Local PORT is optional and is not needed by Vercel Functions.

Register PARTNER_ORIGIN in the backend application's **Test** origins, even when the demo itself is deployed publicly over HTTPS. Test/live indicates the ticketing environment, not whether the demo uses localhost. Use the stable Vercel project domain initially; each changing preview URL would need its own explicit allowlist entry and matching PARTNER_ORIGIN. No wildcard origins.

Redeploy, then open `/integration` and verify authentication, event reads and checkout availability. An empty connected catalogue means there are no assigned published sandbox events. A green checkout availability label is not a completed provider test.

## 5. Acceptance test

Follow [the testing checklist](testing-checklist.md) and record the results. Return confirmation requires the same browser and its signed cookies. Test with separate fictional ordinary/free/group events. Use only Paystack's [official test payment instructions](https://paystack.com/docs/payments/test-payments/) on the sandbox checkout. Keep real card and customer data out of test events.

If API routing fails, verify that api/index.mjs is deployed as a function and the explicit rewrites remain present. The output directory must be public, while server/ and api/ remain server code. Never fix a routing error by copying server code or environment files into public/.
